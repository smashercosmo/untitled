# Void (void.cloud) — facts relevant to this project (2026-11-11)

Source: void.cloud docs, via Context7 `/websites/void_cloud`. Void is a CLI, platform and full-stack SDK for Vite apps, made by Cloudflare.

## Deploy targets

- **Direct Cloudflare**: `void deploy --platform cloudflare`. Deploys into *your* account; you sign in through the browser. In CI it uses `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`. **This project uses this target (Q22).**
- **Void platform**: a self-hosted installation; a team platform also needs Workers for Platforms. The core installation has no custom domains. Raw `cloudflare.*` bindings (existing D1 by ID, native Durable Objects, Workflow classes) are documented for direct Cloudflare deploys only.
- "Named Cloudflare environments aren't supported": use a separate Void project config for each target.
- Native apps work on Workers Free.

## Config

- `void.config.ts` → `defineConfig({ worker: {...}, cloudflare: {...}, inference: {...} })`.
- Existing or extra D1 databases: `cloudflare.d1_databases: [{ binding, database_name, database_id }]`. Settings here override `void.lock.json`.
- `inference.bindings` enables, disables or renames inferred bindings, e.g. `{ "db": "MY_DB" }`.
- **Trap:** if `void deploy` finds a root `wrangler.jsonc` or `wrangler.json`, it offers to link that Worker and migrate its config into `void.config.ts`. That's why the sync Worker's config lives in `workers/sync/`, never at the repo root.
- `void project delete` doesn't remove Cloudflare resources. A failed build can leave provisioned resources behind.

## Database (`void/db`)

- Drizzle ORM. The schema is `db/schema.ts`, the source of truth. `void db generate` writes SQL migrations to `db/migrations/`, which are applied on deploy.
- `void db generate` also includes Void-managed auth tables.
- `createDb(env.OTHER_DB)` returns a Drizzle instance for another D1 binding, typed with the app's own schema.
- Direct Cloudflare D1 migrations use the binding's `migrations_dir`, migrations table and pattern. **`migrations_dir` must be set.**
- Deploy runs a read-only drift check, comparing the schema against the last snapshot (not the live database). If a migration would be generated, deploy stops.
- `void db seed` resets the local database, re-applies migrations, then runs `db/seed.ts` or `db/seed.sql`.
- **Implication (Q26):** the TMDB tables must never be defined in the app's `db/schema.ts`. The app reads them through the Drizzle definitions exported by `packages/tmdb`.

## Learned while building `apps/web` (Void 1.7.0, 2026-11-11)

- **Requirements:** Node ≥ 24.22 or ≥ 26.12 (`create-void` refuses older versions). The repo enforces this with `devEngines.runtime` (`node ^24.22.0`, `onFail: "download"`) in the root `package.json`: pnpm downloads a matching Node and runs scripts and `pnpm exec` with it, so `pnpm exec void …` works even on an older system Node, but a bare `npx void …` doesn't. *(Superseded: this used to say the app was pinned with `mise.toml`; no such file exists.)*
- **Scaffolding without prompts:** `pnpm dlx create-void@1.7.0 web --toolchain vite --framework react --starter sqlite --deploy none`. It creates a standalone pnpm project (its own `pnpm-workspace.yaml` and lockfile); delete those to join a monorepo. The scaffold's `AGENTS.md` points to the bundled docs in `node_modules/void/docs/`, which match the installed version exactly.
- **SPA + API:** `index.html` and `src/` hold the React app; `routes/api/**` holds the Hono handlers (`defineHandler`, `defineHandler.withValidator({ query: zod })`). Use `@vitejs/plugin-react` rather than `voidReact()`, which is for Pages mode.
- **Client imports:** in an SPA, import from `void/client/react`, which exports `auth` (Better Auth React client with `auth.useSession()`, `auth.signUp.email`, `auth.signIn.email`, `auth.signOut`), typed `fetch` and `FetchError`.
- **Typed fetch:** `fetch('/api/movies/:id', { params })` infers the response from the handler's **returned plain object**. Returning `c.json(…, status)` unions breaks the inference (the type becomes `never`).
- **SPA 404 fallthrough:** any 404 from an API route, thrown `HTTPException(404)` or `c.json(…, 404)`, comes back as `index.html` with status 200, at least in dev. 400 and 401 pass through. Model "not found" as data.
- **Auth tables:** `user`, `session`, `account`, `verification` (text IDs), generated by `void db generate` into `db/migrations/`. The local migration history is the `_void_migrations` table (`name`, `applied_at`).
- **Migration guard:** `void db migrate` refuses when the database has tables but `_void_migrations` is empty, and suggests `void db reset` (destructive). Either run Void's migrations first on a fresh database, or adopt: run the SQL once, then insert the filename into `_void_migrations`.
- **Local D1 identity:** the `void db …` CLI resolves `preview_database_id`, then `database_id`, then `binding` (`dist/local-d1-*.mjs`), the same as Wrangler. **The Vite dev server (`@cloudflare/vite-plugin`) uses `database_id`** and ignores `preview_database_id`. To share a local database with another Worker, set `database_id` to the same placeholder locally, together with the same `voidPlugin({ persistTo })` directory. Wrangler's `--persist-to X` and `persistTo: X` both store under `X/v3`.
- **First direct Cloudflare deploy** (`void deploy --platform cloudflare`, 2026-11-11):
  - Needs `void cloudflare login`, a browser OAuth separate from Wrangler's. In a non-interactive shell it uses the single account automatically.
  - Steps: build, save a **D1 restore point** (prints `void db restore --bookmark=…`), apply pending `db/migrations` (the confirmation prompt auto-answers yes when there's no terminal), upload, publish to `https://<cloudflare.name>.<subdomain>.workers.dev`.
  - It used the configured `database_id`; nothing was provisioned.
- **Build output:** goes to `.cloudflare/output/v0/workers/default/` (gitignored). The `void prepare` postinstall generates `.void/` (route types, DB types, Better Auth schema).

## Jobs, queues and durable state

- Cron jobs: `crons/*.ts` with `export const cron = '…'` and `defineScheduled(handler)`.
- Queues: `queues/<name>.ts` with `defineQueue<T>()`. Options are only `maxBatchSize` (10), `maxBatchTimeout` (5 s), `maxRetries` (3) and `retryDelay` (0).
- **Void-managed queues have no dead-letter queue** (exhausted messages are deleted) and no documented `max_concurrency`. That's why the sync pipeline is a separate Wrangler Worker (Q10, Q18, Q23).
- Durable Objects: `durable-objects/*.ts` with `defineDurableState()` or `defineDurableObject()`.
